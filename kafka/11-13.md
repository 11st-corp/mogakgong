# Kafka Connect

- DB, Key-value 저장소, 검색 인덱스 및 파일 시스템 간의 간단한 데이터 통합을 위한 **중앙 집중식 데이터 허브 역할**을 하는 Apache Kafka의 구성요소
  - Apache Kafka 오픈소스 프로젝트 중 하나로 **DB 같은 외부 시스템과 Kafka를 손쉽게 연결하기 위한 프레임워크**

Producer와 Consumer를 직접 개발해 원하는 동작을 실행하고 처리할 수 있으나, 이런 애플리케이션 개발과 운영에 들어가는 리소스나 비용 부담이 큰 경우 Kafka Connect를 사용하면 좀 더 효율적이고 빠르게 클라이언트를 구성하고 적용할 수 있다. 운영자는 Kafka Connect에서 제공하는 REST API를 통해 빠르고 간단하게 Connect의 설정을 조정해 상황에 맞는 유연한 대응을 할 수 있다. ([Connector 목록](https://www.confluent.io/product/connectors))

### Terminology

- Connect
  - Connector를 동작하게 하는 프로세서 (서버)
- Connector
  - Data Source의 데이터를 처리하는 소스가 들어있는 jar 파일 (위 Connector 목록 참조)
- Source Connect
  - Data Source의 데이터를 Kafka 토픽에 보내는 역할을 하는 커넥터 (Producer)
- Sink Connect
  - Kafka 토픽에 담긴 데이터를 특정 Data Source로 보내는 역할을 하는 커넥터 (Consumer)
- Task
  - Connector가 정의한 작업을 직접 수행, Task 또한 Source/Sink Task로 구분
- Standalone Mode
  - 하나의 Connect만 사용하는 모드
- Distributed Mode
  - 여러 개의 Connect를 한개의 클러스터로 묶어서 사용하는 모드. 특정 Connect에 장애가 발생해도 나머지 Connect가 대신 처리할 수 있음

### 동작

![How Kafka Connect Works](https://blog.kakaocdn.net/dn/cgxxbl/btq4YseQUzx/K3IVPWRWzShkJrlE8kHpNk/img.png)

분산 배치된 각 Tasks는 메시지들을 Source에서 Kafka / Kafka에서 Sink로 이동시킨다. 이 때 Connect는 Partitioning 개념을 적용해 데이터를 하위 집합으로 나눈다. Kafka에서의 병렬 처리를 위해 Partitioning하는 것과 동일한 개념. (다만 서로 이름만 동일할 뿐 관계는 없음)
Connector에서 복사되어야 하는 데이터는 레코드 순서에 맞추어 Partitioning해야 한다. 각 Partition에는 Offset이 함께 포함되어서 Connect에 장애/실패가 발생하면 지정된 위치부터 데이터를 이동시킬 수 있다. (Connector에 따라 Offset 기준이 다른데, 일반적인 파일을 전송하는 Connector의 경우 Offset이 파일 위치를 나타내며 데이터베이스의 경우에는 Timestamp나 Seq ID를 나타낸다.)

## CDC (Change Data Capture)

![CDC](https://velog.velcdn.com/images/chan9708/post/3e0a3bd7-1dd8-4ceb-a302-2678f21585fb/image.png)

데이터 변경사항을 식별하고 추적할 수 있는 소프트웨어 디자인 패턴. 데이터 변경이 발생되면 부가적인 동작을 취하는 것이 목적

Source 시스템에서 데이터가 변경되는 것을 감지하여 Target 시스템이 변경 작업에 대응하는 작업을 수행하도록 하는 프로세스

- Pull 방식
  - Target 시스템의 주기적인 Polling으로 변경사항이 있는지 확인하는 방법
  - 쉽게 구현할 수 있으나 실시간성이 떨어짐
- Push 방식
  - Source 시스템이 변경 발생될 때마다 Target 시스템에 알리는 방법
  - Pull 방식에 비해 Source 시스템이 많은 작업을 해야 하고 Target 시스템에 문제가 발생하면 변경 이벤트에 누락이 발생할 수 있으나, 실시간성이 뛰어남

### Debezium

![Debezium Architecture](https://debezium.io/documentation/reference/2.0/_images/debezium-architecture.png)

DB에서 발생하는 변경사항을 추적할 수 있는 Kafka Connect의 Source Connector, 각 Connector는 해당 DB의 CDC 관련 기능을 활용해 변경된 데이터 정보를 가져와서 성공적으로 Commit이 발생한 데이터에 대해서만 변경사항을 전파함 (따라서 실패 트랜잭션은 고려할 필요가 없음). 또한 변경사항을 디스크에 저장하기 때문에 데이터의 변경사항을 전달받아야하는 애플리케이션이 다운되어도 문제 없음

#### Common Use Cases

- Cache Invalidation
  - 애플리케이션 레벨에서 캐시 무효화 로직 분리 가능
- Simplifying Monolithic Application
  - 애플리케이션 코드 작성을 하다보면 DB 데이터 수정, 캐시 무효화, Kafka 데이터 전송 등 여러 외부 시스템으로의 쓰기 작업을 하나의 트랜잭션으로 묶어 Atomicity를 보장해야 하는 경우가 있는데 (Dual-write) 이는 하나의 트랜잭션으로 잘 묶이지 않을 뿐더러 중간에 데이터 손실 가능성이 있어 운영 비용이 높아진다. Debezium을 통해 DB 관련 작업만 하나의 Transaction으로 묶고 Debezium의 CDC 기능을 활용해 외부 시스템에 변경사항 전파 가능
- Sharing Databases
  - 하나의 DB를 여러 애플리케이션이 함께 사용하는 경우 애플리케이션 A가 특정 데이터 변경사항이 발생했을 때 또 다른 애플리케이션 B가 해당 변경사항을 추적하는 것이 쉽지 않다. (Message Bus를 활용할 수 있으나 근본적인 Dual-write 문제가 해결되지 않음) Debezium을 사용하면 여러 애플리케이션에서 특정 데이터 변경사항을 쉽게 추적할 수 있다.
- Data Integration
  - 하나의 데이터는 항상 하나의 시스템에만 저장되지 않을 수 있다. (형태가 변경되거나 저장소 종류가 바뀔 수 있다.) 여러 시스템에 특정 데이터를 일관되게 저장하기 위해 Debezium을 사용할 수 있다.
- CQRS (Command Query Responsibility Segregation)
  - 데이터에 수정이 발생되면 읽기를 위한 데이터도 업데이트되어야 하는데 Debezium을 통해 수정을 위한 데이터 모델과 읽기를 위한 데이터 모델을 동기화하는 로직의 복잡도를 낮출 수 있다.
  > CQRS란 수정을 위한 데이터 모델과 읽기를 위한 데이터 모델을 별도로 분리하는 설계 방식을 의미한다.

# Kafka의 발전과 미래

## Zookeeper 없는 Kafka의 미래

- 기존 버전에서는 Zookeeper에 대한 의존성이 높음
  - Zookeeper는 매우 단순하고 안정적인 애플리케이션으로써 많은 분산 애플리케이션들의 Coordinator 역할을 함
  - Zookeeper 사용에 따른 제약사항
    - Consumer의 Offset 저장소 전환
      - Kafka 2.X 이전에는 Consumer 그룹의 저장소로 Zookeeper의 ZNode 이용
      - 메시지 / Offset / Consumer 증가로 부담 -> Kafka 0.10 부터 Kafka 내부 Topic `_consume_offsets`로 이전하면서 의존성 제거
    - 각기 다른 애플리케이션 운영 부담
      - Zookeeper / Kafka는 별개 프로젝트로, 서로 추구하는 방향성도 다름
      - 각기 다른 API 사용에 따른 부담 -> 개발생산성 저하
      - 운영의 어려움
      - 보안 이슈
      - 메타데이터 관리
        - Zookeeper와 컨트롤러 간의 불일치 (서로 다른 애플리케이션이므로 동기화 시간 발생, 이 때 발생되는 메타데이터 관리 문제)
  
## Zookeeper 의존성 제거한 Kafka 업그레이드

- Zookeeper 의존성 제거를 위해 Zookeeper에 저장한 메타데이터를 Kafka로 이동시킨다.
  - AS-IS : Zookeeper를 통해 선정된 Broker 중 하나의 Controller가 Zookeeper와 통신을 담당하여 메타데이터 업데이트 등 역할, 컨트롤러는 이러한 메타데이터를 나머지 Broker에 Push
  - TO-BE : Zookeeper 역할을 대체하는 컨트롤러, 컨트롤러 노드에도 하나의 Leader 존재, Controller가 Push하는 방식이 아닌 컨트롤러로부터 Pull 방식으로 변경

## KRaft

- AS-IS : Zookeeper 합의 프로토콜을 이용해 Replication 커밋 처리, Leader 선출 동작 처리
- TO-BE : 새로운 합의 프로토콜 필요 -> Raft 합의 프로토콜과 Kafka 특성을 추가한 KRaft 합의 프로토콜 개발
  - Raft는 내부적 합의를 통해 정보를 유지 - 과반수 찬성 방식을 따르기 때문에 장애 발생해도 안정적으로 서비스 가능
  - Node는 Follower / Candidate / Leader 총 3가지 상태
    - 처음 시작은 모든 Node가 Follower
    - Node들은 Leader로부터 Heartbeat를 받아 활성 상태 체크, 타임아웃 시간동안 Heartbeat를 받지 못하면 Follower 상태는 Candidate로 바뀜 -> 다른 Node에 투표 요청
    - Candidate 상태의 Node가 다른 Node로부터 과반수 이상 투표를 받으면 새로운 Leader Node로 변경
  - KRaft는 주기적으로 스냅샷 생성

## 최적화된 컨트롤러 노드 구성

- 클러스터 내 임의 브로커 3개 선정 / 동일한 노드에서 브로커 프로세스와 컨트롤러 프로세스 실행 -> 별도 서버가 필요하지 않으므로 서버 절약 가능
- 클러스터 내 실행되는 브로커 노드와 컨트롤러 노드 관리 / 별도 서버 구성 -> 장애시 안정성 확보, 각 노드에 할당된 리소스 단독으로 사용 가능
