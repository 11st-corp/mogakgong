# [스키마 레지스트리](https://docs.confluent.io/platform/current/schema-registry/index.html)

Kafka 데이터 흐름이 대부분 Broadcast 방식이여서 Producer를 신뢰할 수밖에 없다. 그래서 Producer 관리자가 Topic Data를 Consume하는 관리자에게 이 데이터 구조를 설명해줘야하는데 이 작업이 매번 일일이 해줘야한다는 점에서 불편하다. 따라서 데이터에 대한 정확한 정의와 의미를 스키마를 통해 전달할 수 있다.

## Schema

데이터의 구조와 제약조건에 관한 전반적 명세를 기술한 것이다.

## Schema Registry

![Schema Registry](https://docs.confluent.io/platform/current/_images/schema-registry-ecosystem.jpg)

Schema Registry는 Kafka에서 Schema를 등록하고 관리하는 별도의 애플리케이션이다. Producer와 Consumer는 이 Schema Registry와 직접적으로 통신하면서 데이터를 직렬화/역직렬화한다. 이 때 사용하는 포맷은 **Avro**이다. (물론 JSON, Protocol Buffer도 지원하지만 가장 권장되는 방식은 Avro이고 그 이유는 다음과 같다: **Avro는 JSON과 매핑된다는 점, Avro는 간결한 데이터 포맷이라는 점, 바이너리 형태로 매우 빠르다는 점 (JSON은 메시지마다 Field Name이 포함돼 전송 효율이 떨어진다.)**)

### [Apache Avro](https://avro.apache.org/)

> 데이터 직렬화 시스템

Apache에서 만든 프레임워크로, RPC(Remote Procedure Call)와 데이터 직렬화를 제공한다. 언어 중립적이고, JSON과 형식은 비슷하지만 **스키마가 존재한다는 차이가 있다.** 또한 데이터가 CSV, XML, JSON, Binary 등으로 다양하게 직렬화가 가능한데, 이 때 Binary의 경우 파싱 시간이 짧아져 퍼포먼스 개선의 효과가 있다.

### Avro Schema

확장자는 `.avsc`를 사용한다.

```json
{
  "namespace": "example.avro",
  "type": "record",
  "name": "User",
  "doc": "Represents User",
  "fields": [
      { "name": "name", "type": "string" },
      { "name": "favorite_number",  "type": ["int", "null"], "doc": "Favorite Number" },
      { "name": "favorite_color", "type": ["string", "null"], "doc": "Favorite Color" }
  ]
}
```

- `namespace` : 이름 식별 문자열
- `type` : 다음 타입을 지원한다.
  - `record`
  - `enums`
  - `arrays`
  - `maps`
- `doc` : 주석, 사용자에게 이 스키마 정의에 대한 설명을 표현한다.
- `name` : 레코드 이름을 나타내는 문자열
- `fields` : 필드 리스트
  - `name` : 필드명
  - `type` : 데이터 타입 정의로 아래 타입이 있다.
    - `boolean`
    - `int`
    - `long`
    - `string`
  - `doc` : 주석, 사용자에게 해당 필드의 의미를 표현한다.

아래와 같이 스키마를 읽어와 직렬화 / 역직렬화한다.

```java
Schema schema = new Schema.Parser().parse(new File("user.avsc"));

GenericRecord user1 = new GenericData.Record(schema);
user1.put("name", "Alyssa");
user1.put("favorite_number", 256);

GenericRecord user2 = new GenericData.Record(schema);
user2.put("name", "Ben");
user2.put("favorite_number", 7);
user2.put("favorite_color", "red");

File file = new File("users.avro");
DatumWriter<GenericRecord> datumWriter = new GenericDatumWriter<GenericRecord>(schema);
DataFileWriter<GenericRecord> dataFileWriter = new DataFileWriter<GenericRecord>(datumWriter);
dataFileWriter.create(schema, file);
dataFileWriter.append(user1);
dataFileWriter.append(user2);
dataFileWriter.close();

DatumReader<GenericRecord> datumReader = new GenericDatumReader<GenericRecord>(schema);
DataFileReader<GenericRecord> dataFileReader = new DataFileReader<GenericRecord>(file, datumReader);
GenericRecord user = null;
while (dataFileReader.hasNext()) {
  user = dataFileReader.next(user);
  System.out.println(user);
}
```

필요한 경우 정의된 스키마를 코드로 자동 변환 또한 가능하다.

java -jar /path/to/avro-tools-1.11.0.jar compile schema user.avsc .

### 동작 방식

![Schema Registry Architecture](https://docs.confluent.io/platform/current/_images/schema-registry-and-kafka.png)

1. 로컬 캐시에 없으면 스키마 전송 (등록)
  - Avro Producer는 Confluent에서 제공하는 `KafkaAvroSerializer`라는 새로운 직렬화를 사용해서 스키마 레지스트리의 스키마가 유효한지 따져본다. 스키마가 확인되지 않으면 Avro Producer가 스키마를 등록하고 캐시한다.
2. 스키마 등록 (ID 할당)
  - 스키마 레지스트리가 현재 스키마가 저장소의 스키마와 동일한 것인지, 변경된 것인지 확인한다.
  - 스키마 레지스트리 자체적으로 각 스키마별로 고유 ID를 할당한다. 순차적으로 1씩 증가하지만 반드시 연속적이지는 않다.
  - 스키마에 문제가 없다면 스키마 레지스트리는 Producer에 고유 ID를 응답한다.
3. 스키마 ID별 Avro 메시지 직렬화 전송
  - Producer는 스키마 레지스트리로부터 받은 스키마 ID를 참고해서 메시지를 Kafka로 전송한다. 이 때 스키마 전체 내용이 아닌 메시지와 스키마 ID만 보낸다. **Avro를 사용하면 JSON이 `key:value` 형태의 전체 메시지를 전송하는 반면 스키마 ID 및 value만 보내기 때문에 메시지 크기를 줄일 수 있는 것이다.**
4. 로컬 캐시에 없으면 스키마 ID별로 가져오기
  - Avro Consumer는 스키마 ID로 Confluent에서 제공하는 `KafkaAvroDeserializer`라는 새로운 역직렬화를 사용해서 Topic의 메시지를 읽는다. 이 때 Consumer에 스키마 ID가 없다면 스키마 레지스트리로부터 가져온다.

> 스키마를 직렬화 / 역직렬화할 때는 별개의 Avro Producer와 Avro Consumer가 필요하다.

### [스키마 레지스트리 호환성](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)

![Schema Compatibility](https://developer.confluent.io/5c940ba0a60bc5e46ecbd96292695fe6/schema-compatibility.svg)

스키마 레지스트리 입장에서는 Producer가 Topic에 메시지를 생성하고 Consumer가 Topic의 메시지를 소비하기까지 **스키마 관리**, **Producer의 메시지 유효성 검사**, **Consumer의 메시지 유효성 검사**를 수행해야 한다. 운영 중 스키마가 변경되는 경우에 대해서 고려해야 할 필요가 있을텐데, 스키마 레지스트리에서는 버전별 스키마에 대한 관리를 효율적으로 해주며 각 스키마에 대해 고유 ID와 버전 정보를 관리한다.

스키마는 하나만 존재하는게 아니라 여러 버전이 존재할 수 있고 스키마를 변경하는 시나리오가 다를 수 있기에 여러 호환성 모드를 제공하는데 대표적으로는 `FORWARD`, `BACKWARD`, `FULL` 호환성 레벨을 제공한다.

#### BACKWARD 호환성

![Backward Compatibility 1](https://images.ctfassets.net/gt6dp23g0g38/5DnDbqiplI2m88vIFhN1am/b698815400ab7c0620836d8c5226e186/sr101-m10-08.png)

![Backward Compatibility 2](https://images.ctfassets.net/gt6dp23g0g38/dDYU3CfjAAamMMpFdsVOS/7270015819fb8782476ec66240703c4e/sr101-m10-09.png)

- 변경된 스키마를 적용한 Consumer가 변경 전 스키마가 적용된 Producer가 보낸 메시지를 읽을 수 있도록 허용
- 새로운 필드를 추가할 때는 이를 Optional 필드로 설정하고, 기존 필드를 유지한다. 이렇게 하면 이전 버전 Consumer가 새로운 스키마로 생성된 데이터를 문제 없이 처리할 수 있다.

|호환성 레벨|지원 버전 (Consumer 기준)|변경 허용 항목|스키마 업데이트 순서|
|--------|----------------------|-----------|--------------|
|BACKWARD|자신과 동일한 버전과 하나 아래의 하위 버전|필드 삭제, 기본값 지정된 필드 추가|Consumer -> Producer|
|BACKWARD_TRANSITIVE|자신과 동일한 버전을 포함한 모든 하위 버전|상동|상동|

#### FORWARD 호환성

![Forward Compatibility 1](https://images.ctfassets.net/gt6dp23g0g38/5ckq7Z1abCO3UMTHAaNLMj/efadfd9b1a080a01429a5a3bdb6c8ae4/sr101-m10-10.png)

![Forward Compatibility 2](https://images.ctfassets.net/gt6dp23g0g38/5g5MWiPLfuCtTAOZdJUew9/4cee1c58c2eecbcf56b5d7908eb59581/sr101-m10-11.png)

- 변경된 스키마가 적용된 Producer가 보낸 메시지를 변경 반영 전인 스키마를 적용한 Consumer가 읽을 수 있도록 허용
- 기존 필드 제거 없이 새로운 필드를 추가하는 경우, 이전 버전 Producer가 생성한 데이터는 새로운 버전 Consumer가 처리할 수 있어야 한다. 즉, 새로운 Consumer는 모든 필드가 필수가 아니라고 가정하고 작동해야 한다.

|호환성 레벨|지원 버전 (Consumer 기준)|변경 허용 항목|스키마 업데이트 순서|
|--------|----------------------|-----------|--------------|
|FORWARD|자신과 동일한 버전과 하나 위의 상위 버전|필드 삭제, 기본값 지정된 필드 삭제|Producer -> Consumer|
|FORWARD_TRANSITIVE|자신과 동일한 버전을 포함한 모든 상위 버전|상동|상동|

#### FULL 호환성

![Full Compatibility](https://images.ctfassets.net/gt6dp23g0g38/64wBrgMQbDnxVdyhXbE2es/88078116f6a81a2cfdecb691f26514aa/sr101-m10-12.png)

- 스키마가 위의 두 호환성을 모두 만족하는 경우
- Producer는 새로운 필드를 추가하거나 기존 필드를 수정할 때, 이전 버전 Consumer와 신규 버전 Consumer 모두 호환될 수 있도록 한다. 이를 위해 새로운 필드를 Optional로 추가하고, 중요한 필드를 제거하지 않는다.

|호환성 레벨|지원 버전 (Consumer 기준)|변경 허용 항목|스키마 업데이트 순서|
|--------|----------------------|-----------|--------------|
|FULL|자신과 동일한 버전과 하나 위 혹은 하나 아래 버전|기본값 지정된 필드 추가, 기본값 지정된 필드 삭제|무관|
|FULL_TRANSITIVE|자신과 동일한 버전을 포함한 모든 상위 및 하위 버전|상동|상동|
