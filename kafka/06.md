# 컨슈머의 내부 동작 원리와 구현

---

## 컨슈머 오프셋 관리

- 컨슈머가 일시적으로 동작을 멈추고 재시작하는 경우나, 컨슈머가 구동 중인 서버에서 문제가 발생해 새로운 컨슈머가 기존 컨슈머의 역할을 대신하는 경우에는 기존 컨슈머의 마지막 메시지 위치부터 새로운 컨슈머가 메시지를 가져올 수 있어야만 장애에서 빠르게 복구 가능
  - 따라서 컨슈머의 오프셋 관리는 매우 중요하다.
  - **숫자 형태로 나타내며 컨슈머 그룹이 자신의 오프셋 정보를 가장 안전한 저장소인 Topic에 저장**한다. (`__consumer_offsets`, 각 그룹별로 기록)

### `__consumer_offsets` 구성

- `offsets.topic.num.partitions`: Default 50
- `offsets.topic.replication.factor`: Default 3

## 그룹 코디네이터

![Group Coordinator](https://images.ctfassets.net/gt6dp23g0g38/6smQqDfuZgjNPFeB7iNHLb/d237de3390dcb0cada914c06f4142053/Kafka_Internals_065.png)

- 컨슈머 그룹에서는 각 컨슈머가 언제든 그룹에서 떠날 수 있으며, 새로 합류할 수도 있다.
  - 컨슈머 그룹은 이러한 변화를 인지하고 각 컨슈머들에게 작업을 균등하게 분배해야 한다. (**리밸런싱**)
  - 이러한 리밸런싱은 그룹 코디네이터가 수행한다.
    - 컨슈머 그룹이 구독한 토픽의 파티션들과 그룹의 멤버들을 tracking한다.
    - 그룹 코디네이터는 브로커 중 하나에 위치한다. 컨슈머 그룹이 브로커에 최초 연결 요청을 보내면 브로커 중 하나에 그룹 코디네이터가 생성되며 이 그룹 코디네이터는 컨슈머 그룹의 컨슈머 변경과 구독하는 토픽 파티션 변경 등에 대해 Tracking을 시작한다.
    - 토픽 파티션이나 그룹 내 멤버 변경이 발생하면 변경사항을 컨슈머들에 통지한다.

### Consumer Heartbeat

- `heartbeat.interval.ms` (Default : 3000)
  - 그룹 코디네이터와 Heartbeat Interval
  - `session.timeout.ms`보다 낮게 설정해야 (1/3 수준 적절)
- `session.timeout.ms` (Default : 10000)
  - 어떤 컨슈머가 특정 시간 안에 Heartbeat를 받지 못하면 문제가 발생했다고 판단해 Consumer Group에서 해당 Consumer를 제거하고 리밸런싱
- `max.poll.interval.ms` (Default : 300000)
  - 컨슈머가 주기적으로 poll() 호출해 토픽으로부터 레코드를 가져오는데 해당 호출 후 최대 5분간 다음 poll() 호출이 없는 경우 컨슈머에 문제가 있는 것으로 판단하여 리밸런싱

## 스태틱 멤버십 (Kafka 2.3 ~ )

![Static Membership](https://images.ctfassets.net/gt6dp23g0g38/4nNPDs11L8OfiTtOfl7Ket/6b08a07f522090245224538c9f621c04/Kafka_Internals_082.png)

- 컨슈머 그룹 내에서 컨슈머가 재시작 등으로 그룹에서 나갔다가 재합류하더라도 리밸런싱이 일어나지 않도록 하는 영속적 멤버
  - 컨슈머마다 인식할 수 있는 ID(`group.instance.id`)를 적용해 기존 구성원임을 인식
  - 불필요한 리밸런싱을 줄일 수 있다.

- `session.timeout.ms`를 기본값보다 큰 값으로 조정해야 한다. 해당 시간 내 컨슈머가 재시작하고 그룹 코디네이터가 Heartbeat를 받지 못하면 강제 리밸런싱이 발생되어 스태틱 멤버십 목적에 위배되기 때문이다.

## 컨슈머 파티션 할당 전략

![Range Partition Assignment Strategy](https://images.ctfassets.net/gt6dp23g0g38/2I7BijMOpFeFxkdeyH5kFN/9f00009b876cf3339d6c646e53143cd8/Kafka_Internals_069.png)

- 레인지 파티션 할당 전략
  - 기본 전략으로, 토픽별 할당 전략을 사용
  - 동일한 키를 이용하는 2개 이상의 토픽을 Consume할 때 유용함

![Round Robin / Sticky Partition Assignment Strategies](https://images.ctfassets.net/gt6dp23g0g38/4OL5b1FeAv3mSXM99a5IxA/2ea543db29d3d1a0b26cf57a312208ab/Kafka_Internals_070.png)

- 라운드 로빈 파티션 할당 전략
  - 사용 가능한 파티션과 컨슈머들을 라운드 로빈으로 할당함. 균등 분배 가능
- 스티키 파티션 할당 전략
  - 컨슈머가 Consume하는 파티션을 계속 유지 가능


- 협력적 스티키 파티션 할당 전략
  - 스티키 방식과 유사하나 전체 일시 정지가 아닌 연속적 재조정 방식

## 정확히 한 번 컨슈머 동작

- 프로듀서의 `정확히 한 번 전송` 동작을 위해 브로커 측에서는 트랜잭션 관리 및 프로듀서의 동작을 보조하는 별도의 `트랜잭션 코디네이터` 프로세스가 실행된다.
  - `트랜잭션 코디네이터`는 프로듀서의 정확히 한 번 전송이 성공하면 **해당 레코드의 트랜잭션 성공을 표시하는 특수한 메시지를 추가하는데, 따라서 컨슈머에게 이러한 특수한 메시지가 추가된 데이터만 읽도록 설정**하면, 정확히 한 번 컨슈머가 동작할 수 있게 된다.
  - `ISOLATION_LEVEL_CONFIG` 옵션을 `READ_COMMITTED`로 설정하면 이 동작을 활성화할 수 있다.
  - 컨슈머가 트랜잭션 코디네이터와 통신하는 부분이 없으므로 정확히 메시지를 한 번 가져오는지는 보장할 수 없다. 따라서 컨슈머 동작까지 정확히 한 번 처리하려면 `Consume - 메시지 처리 - Producing` 과정을 하나의 트랜잭션으로 처리해야 한다.
    - `sendOffsetsToTransaction` 메서드를 이용해 컨슈머 그룹의 오프셋 커밋을 트랜잭션에 포함시키고, 이 처리 과정이 실패하면 해당 컨슈머 그룹의 커밋 오프셋이 증가하지 않게 해서 실패한 전체 트랜잭션을 다시 시작할 수 있게 한다.
